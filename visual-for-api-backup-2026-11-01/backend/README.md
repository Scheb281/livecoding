# ASP.NET API для interview.

Реализованный бэкенд для существующего React: .NET 10, ASP.NET Identity,
EF Core 10, Npgsql, SignalR. PostgreSQL подключается строкой подключения.
Секреты и реальные данные базы в проект не записаны.

## Подключение к PostgreSQL по шагам

1. В PostgreSQL/pgAdmin создай пустую БД `visual_interview` и пользователя,
   который владеет этой базой и может создавать таблицы в её схеме.
2. Открой терминал в `backend/Interview.Api` и укажи свои значения:

```powershell
dotnet user-secrets set "ConnectionStrings:Database" "Host=localhost;Port=5432;Database=visual_interview;Username=interview_app;Password=ВАШ_ПАРОЛЬ"
dotnet run -- --migrate
```

Команда `--migrate` применяет миграции, создаёт четыре роли и завершает работу.
Все таблицы создаются автоматически. Саму БД можно заранее создать в pgAdmin.
Для этого нужны .NET SDK 10 и доступ к NuGet при первом восстановлении пакетов.

3. Один раз создай первого администратора. Укажи свой email и пароль длиной
   8–128 символов, затем удали начальный пароль из секретов:

```powershell
dotnet user-secrets set "Bootstrap:Email" "admin@example.com"
dotnet user-secrets set "Bootstrap:Name" "Администратор"
dotnet user-secrets set "Bootstrap:Password" "ВАШ_НОВЫЙ_ПАРОЛЬ"
dotnet run -- --bootstrap-admin
dotnet user-secrets remove "Bootstrap:Password"
```

Если администратор уже есть, начальное создание повторно запрещено.
Пароль сохраняет Identity как PasswordHash; публичной регистрации администратора нет.

4. Запусти API:

```powershell
dotnet run
```

Профиль разработки запускает API на `http://localhost:5000`.
`/health/live` проверяет процесс, `/health/ready` — соединение с БД.
В обычном режиме API не применяет миграции сам: обновление схемы запускается отдельно.

5. Во втором терминале, в корне React-проекта:

```powershell
npm install
npm run dev
```

Открой `http://localhost:5173` и войди администратором. Кнопку деморежима
для работы с настоящей БД нажимать не нужно. Vite проксирует `/api` и `/hubs`
на порт 5000. Если API слушает другой адрес, задай ASPNET_URL и перезапусти Vite.

## Первый рабочий сценарий

1. Администратор создаёт тимлида и интервьюера. После создания фронтенд показывает
   одноразовую ссылку установки пароля. Передай её соответствующему сотруднику.
   Письма автоматически не отправляются. Ссылка действует 24 часа и хранится
   в БД только в виде SHA-256-хеша.
2. Сотрудник открывает ссылку, устанавливает пароль и получает свою серверную роль.
3. Тимлид создаёт рубрику. Интервьюер или тимлид наполняет банк задач.
4. Интервьюер создаёт комнату, выбирает задачи и рубрику, запускает её,
   получает одноразовую ссылку кандидату сроком на час.
5. Кандидат может заранее зарегистрироваться либо войти гостем по приглашению.
   Регистрация сама по себе доступа к интервью не даёт. Погашение приглашения
   связывает текущий аккаунт кандидата с комнатой.
6. Кандидат пишет код, интервьюер видит сохранённые изменения в реальном времени.
   Чат и подсказки сохраняются в БД; SignalR уведомляет об изменениях.
7. Интервьюер выставляет оценку, кандидат отправляет неизменяемый снимок решения,
   тимлид получает отчёт, администратор видит аудит.

Для разных ролей используй разные профили браузера/инкогнито: cookie-сеанс
общий для вкладок одного профиля. У комнаты один кандидат и один владелец-интервьюер.
Интервьюер может наблюдать из нескольких вкладок. Для кандидата одновременно
разрешена одна вкладка-писатель; вторая получит понятный отказ.

## Что где лежит

- `Interview.Api/Program.cs` — настройка DI, cookie, CSRF, Origin, ограничений запросов.
- `Models/Entities.cs` — сущности и поля таблиц.
- `Data/AppDbContext.cs` — ключи, связи, индексы, ограничения и типы PostgreSQL.
- `Data/Migrations/` — сгенерированная EF Core-миграция и снимок модели.
- `database/initial-schema.sql` — идемпотентный PostgreSQL-скрипт той же миграции.
- `Contracts/Dtos.cs` — входящие и исходящие данные API.
- `Controllers/` — HTTP API, доступ, валидация, операции с базой.
- `Hubs/InterviewHub.cs` — вход в комнату и обновление общего кода.
- `Services/RoomConnections.cs` — комнаты соединений и единственный писатель.
- `Services/RunService.cs`, `RunWorker.cs` — квота, очередь и HTTP-клиент sandbox.
- `Interview.Api.Tests/` — интеграционные тесты HTTP, БД и SignalR.

Основные функции снабжены пояснениями. Начинай чтение с Program.cs,
затем выбери нужный Controller и соответствующую модель.

## Таблицы и создание схемы

SQL создаёт 28 таблиц: 7 стандартных таблиц Identity, 20 прикладных и
`__EFMigrationsHistory`. Точный SQL с типами и ограничениями — в
`database/initial-schema.sql`. Создавать таблицы по одной вручную не требуется.

Прикладные таблицы: Tasks, TaskTests, Rubrics, RubricCriteria, Interviews,
InterviewTasks, Invitations, PasswordSetups, CodeDocuments, CodeEvents,
ChatMessages, Hints, HintUsages, Evaluations, EvaluationScores, Submissions,
CodeRuns, CodeRunTests, DailyRunUsages, AuditEvents.

Id пользователя — text, остальные Id — uuid; даты/время — timestamptz UTC,
суточная дата квоты — date, версии/баллы/лимиты — integer, флаги — boolean.
Снимки задач и рубрик — jsonb, теги — text[]. SHA-256 токена сохраняется
64-символьной hex-строкой, а не открытым токеном. Полные имена и размеры
полей определены миграцией, она является источником схемы.

Изменение задачи в банке не меняет снимок в комнате. История кода хранит
подтверждённые версии. Сдача решения не меняется после дальнейшей правки кода.
Уникальные индексы защищают повторное использование mutationId, версии кода,
учёт подсказки и повторную сдачу той же версии решения.

Если хочешь применить SQL вручную через pgAdmin, выполняй его на выбранной
пустой БД. Затем обычный запуск API создаст роли. Не удаляй запись истории
миграций и не смешивай эту схему с таблицами другого приложения.

Из корня backend можно проверить модель и обновить SQL:

```powershell
dotnet tool restore
dotnet ef migrations has-pending-model-changes --project Interview.Api
dotnet ef migrations script --idempotent --project Interview.Api --output database/initial-schema.sql
```

При изменении сущностей сначала создаётся новая миграция, существующая InitialCreate
после выкладки не редактируется. SQLite из тестов не используется рабочим API.

## API и SignalR

Маршруты соответствуют `docs/API_AND_DATABASE.md` в корне фронтенда.
Hub `/hubs/interviews`: `JoinInterview(roomId)` и
`UpdateCode(roomId, { taskId, language, code, baseVersion, mutationId })`.
Подтверждение UpdateCode возвращает DocumentDto с новой version.
`CodeUpdated(document)` получают остальные соединения комнаты.
`RoomChanged` уведомляет о чате, подсказках, оценках и решениях — React
после этого перечитывает комнату через HTTP API из базы.
`AccessRevoked` блокирует редактор при отключении учётной записи.

Код ограничен 20000 символов. Сохранения сериализуются блокировкой транзакции
PostgreSQL и проверкой версии. Погашение приглашения и квота тоже защищены
транзакциями и advisory locks. Скрытые тесты не сериализуются кандидату.
Максимум активных тимлидов — 10, меняется через Security:MaxTeamLeads.

## Выполнение кода: отдельный сервис

В репозитории реализованы очередь, хранение результатов, квоты и адаптер runner.
Сам контейнерный sandbox, который компилирует и выполняет код, сюда не включён.
По умолчанию запуски отвечают 503 с объяснением; квота при этом не расходуется.
API никогда не вызывает Process.Start, Python, bash или dotnet для кода кандидата.

Для своего доверенного sandbox-сервиса настрой Runner:BaseUrl и Runner:ApiKey
через секреты/переменные среды. В BaseUrl включи нужный префикс пути, например
`http://runner:8080/`. Адаптер делает POST `{BaseUrl}/execute` с Bearer-ключом.
Никакие публичные сервисы выполнения по умолчанию не используются.

Запрос:

```json
{
  "runId": "uuid", "language": "Python", "code": "print(5)",
  "timeLimitMs": 2000, "memoryLimitMb": 128,
  "tests": [{ "position": 0, "input": "2 3" }]
}
```

Ответ:

```json
{
  "tests": [{ "position": 0, "output": "5\n", "exitCode": 0,
    "timedOut": false, "durationMs": 15, "memoryKb": 1024 }]
}
```

Сравнение output с ожидаемым ответом выполняет API, учитывая только нормализацию
CRLF и завершающих переводов строк. Вывод скрытых тестов не передаётся в браузер.
Показатель «решил» увеличивается только при отправке точного снимка, прошедшего
все тесты; успешный запуск другой версии не засчитывается.

Runner обязан сам обеспечить одноразовое окружение, отсутствие сети, секретов
и сокета Docker внутри пользовательского контейнера, лимиты процессов/CPU/памяти/
времени/вывода и очистку. HTTP-таймаут API не останавливает удалённый процесс.
Запрос runner ограничен общим ожиданием 45 секунд, ответ — 1 МиБ, видимый вывод
ограничен 32768 символами. Квота резервируется при постановке в очередь;
ошибка runner не возвращает потраченную квоту, чтобы нельзя было обходить лимит.

## Проверки и ограничения

```powershell
dotnet test Interview.sln
dotnet build Interview.sln
```

Интеграционные тесты используют временную SQLite-БД, настоящий ASP.NET pipeline,
Identity, HTTP и два SignalR-клиента. Worker проверяется подставным sandbox:
пользовательский код в тестах не запускается. Генерация PostgreSQL-миграции и
проверка отсутствия расхождений модели выполняются отдельно.
На момент подготовки реальный PostgreSQL не был запущен, миграция на нём
ещё не применялась. После подключения проверь полный сценарий выше.

Текущий реестр соединений и worker рассчитаны на ОДИН процесс API. Несколько
реплик без общего реестра/распределённой аренды писателя запускать нельзя.
Для большого числа записей потребуются пагинация и агрегации отчётов в SQL.
Средний балл задачи — средняя оценка интервью, в которых она назначалась,
а не отдельная оценка алгоритма именно этой задачи.

Перед размещением настрой HTTPS, реальный AllowedHosts, Security:AllowedOrigins
и сохранение ключей ASP.NET Data Protection между перезапусками. За reverse proxy
настрой доверенные прокси и передачу схемы/адреса клиента; произвольным Forwarded
заголовкам доверять нельзя. Иначе ограничения по IP будут видеть адрес прокси.
Строку подключения и ключ runner передавай средой, а не коммить в appsettings.
