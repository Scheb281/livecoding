# Техническая записка: защита и исполнение кода

## Границы системы

React обращается к ASP.NET по HTTPS; SignalR использует защищённый транспорт
того же сайта. ASP.NET хранит данные в PostgreSQL и отправляет задания
отдельному доверенному сервису Interview.Runner. Сам API процессы кандидата
не запускает. Runner управляет Docker на своём узле; для публичной выкладки
размещай его на отдельной машине/VM без базы и ключей приложения.

Docker-контейнер разделяет ядро с Docker-хостом. Поэтому код действительно
исполняется на узле runner, внутри ограниченного контейнера; контейнеризация
не означает отсутствия исполнения на какой-либо VM. Сильнее границу делают
отдельные VM или совместимый sandbox-runtime вроде gVisor. Реестр совместного
редактора и обработчик очереди пока рассчитаны на один экземпляр API.

## Что уже защищено

- Пароли: односторонние хеши ASP.NET Identity, а не обратимое шифрование.
- Приглашения: 32 случайных байта, SHA-256-хеш в БД, TTL, привязка к комнате,
  атомарное одноразовое погашение. Аналогично защищены ссылки установки пароля.
- Cookie: HttpOnly, Secure в production, срок 8 часов, проверка активности
  пользователя и security stamp. Отключение пользователя удаляет его соединения
  из групп SignalR; редактор получает AccessRevoked.
- HTTP-изменения: CSRF-токен. Hub проверяет Origin, роль, членство в комнате,
  текущего писателя и версию документа. URL/поля клиента не выдаёт роль admin.
- Запуски: суточная квота, ограничения частоты, число ожидающих заданий,
  неизменяемая версия исходника. Ошибка runner не возвращает потраченную квоту.
- В production API перенаправляет на HTTPS и включает HSTS. Удалённый runner
  требует HTTPS. В разработке localhost может использовать HTTP.

## Шифрование данных в БД

FieldCipher использует ASP.NET Data Protection: шифрование с проверкой
целостности. Шифруются код и его история, решения, исходники запусков, видимый
вывод, чат, подсказки, комментарии оценок, вход/ожидаемый вывод тестов,
снимки задач/рубрик и payload событий сессии. В БД они имеют префикс
`protected:v1:` и тип text; снимки больше не являются открытым jsonb.

Не шифруются идентификаторы, роли, email для поиска/входа, имена, теги,
условия задач, числовые лимиты/баллы и метаданные событий. Это выборочное
шифрование содержимого, а не шифрование всей базы или диска.
Пароли и токены остаются хешами; расшифровывать их приложению не нужно.

Key ring по умолчанию хранится в пользовательской LocalApplicationData/
visual-interview/keys. В Windows ключи защищаются DPAPI текущего пользователя.
В Linux production требуется PFX-сертификат для шифрования key ring:
Security:KeyEncryptionCertificatePath и его пароль из секретов.
Сам PFX не используется как HTTPS-сертификат сайта.

Создание сертификата уже встроено в API. Из backend/Interview.Api:

```powershell
dotnet user-secrets set "Security:KeyEncryptionCertificatePath" "C:\private-interview\keyring.pfx"
dotnet user-secrets set "Security:KeyEncryptionCertificatePassword" "ВАШ_ПАРОЛЬ_СЕРТИФИКАТА_ОТ_16_СИМВОЛОВ"
dotnet run -- --create-keyring-certificate
```

Папка должна быть закрыта от других пользователей и находиться вне репозитория
и каталога веб-сервера. Для Linux укажи путь вроде /var/lib/interview/keyring.pfx.
Security:KeysDirectory позволяет назначить постоянную папку XML-ключей.
Храни резервные копии БД, key ring, сертификата и его пароля отдельно от кода.
Потеря ключей делает защищённые поля нечитаемыми. Замена сертификата без
сохранения возможности расшифровать старые ключи недопустима.
User-secrets удобен в разработке; в production используй защищённые секреты среды.

## Обновление существующей базы

1. Останови API и сделай резервную копию БД и ключей.
2. Примени новые миграции: `dotnet run -- --migrate`.
3. Выполни `dotnet run -- --encrypt-existing-data`.
4. Запусти API и проверь вход и чтение прежних задач/комнат.

Команда пакетно переписывает прежние строки через шифрование. Новые записи
шифруются автоматически. Совместимость чтения открытых старых строк нужна
только для перехода; без шага 3 старые данные останутся открытыми.
Автоматический откат схемы на старую версию после шифрования не выполняй:
старый код не понимает ciphertext, а прежние varchar-лимиты могут быть короче.
При восстановлении используй согласованную резервную копию БД и ключей.

## Политика sandbox

Один тест — один новый контейнер. Контейнер не получает ключ runner, строку
подключения, ключи Data Protection, Docker socket, host-монты или доступ к сети.
Содержимое файлов одного теста не переносится к следующему.

Параметры: network=none, read-only корень, UID/GID 65532, cap-drop=ALL,
no-new-privileges, pids-limit=64, CPU=1, без swap сверх memory, core=0,
nofile=256, log-driver=none. /work — временная tmpfs для кода и бинарных файлов,
/tmp — отдельная неисполняемая tmpfs. Только /work разрешает исполнение
собранного бинарного файла; каталоги хоста туда не подключаются.

Компиляция получает не меньше 768 МБ и ограничена 30 секундами. После неё
временные кэши удаляются, Docker уменьшает память до значения задачи, и только
потом запускается программа. Runtime ограничивается TimeLimitMs и памятью
задачи. stdout/stderr объединяются и ограничены 32768 байтами на тест.
На весь набор даётся не больше 180 секунд. Ошибка компиляции, runtime error,
timeout, превышение вывода и ресурсы имеют отдельный ErrorKind.

Супервизор внутри контейнера ограничивает дочернюю группу процессов, а finally
на стороне runner делает docker rm --force. Watchdog завершает зависшее ожидание
служебного протокола даже после пропажи runner. При аварии Docker/машины
могут остаться остановленные контейнеры с меткой interview.sandbox=true;
очищать можно только эти контейнеры после проверки, что активных запусков нет.

Ожидаемые ответы остаются в API, runner получает только ввод. API сравнивает
вывод с expected. Вывод скрытых тестов в браузер не попадает, в том числе если
программа пытается напечатать свой вход. Компиляционный процесс ещё не получает
файл stdin.txt со скрытым вводом. На хосте исходник не становится shell-командой:
Docker запускается через ArgumentList, а код передаётся JSON в stdin.

Runner — доверенный компонент с правами управления Docker. Его нельзя публиковать
без аутентификации: POST /execute требует отдельный длинный Bearer-ключ и лимитирует
запросы. Ключ приходит из секретов, а имя образа — из конфигурации оператора,
не из запроса кандидата. В production закрывай доступ сетевыми правилами до API
и используй TLS. Для образов фиксируй digest при выпуске и обновляй базовые образы.

## Совместное редактирование и запись

Упрощённая модель: один общий документ, два возможных автора, передача управления,
курсоры и проверка baseVersion. Интервьюер может взять управление для объяснения,
затем освободить редактор. Это не CRDT/OT и не независимый одновременный ввод
двух писателей: конфликт отклоняется, локальный несохранённый текст не затирается.

SessionRecorder атомарно сохраняет события: создание/открытие/старт/завершение,
код, запуски и результаты, подсказки/использование, чат, сдачу и оценки.
Запись имеет монотонный sequence. Получение событий постраничное; при перемотке
API восстанавливает нужную версию документа, браузер не скачивает всю историю кода.
Оценки и их комментарии имеют staff visibility и исключаются из записи кандидата.
События до появления SessionEvent в старой версии восстановить автоматически
целиком нельзя; прежний CodeEvents остаётся в истории кода администратора.

## Reverse proxy и PostgreSQL

В production замени AllowedHosts и Security:AllowedOrigins на реальные домены.
Security:TrustedProxies принимает только явные IP доверенных прокси для
X-Forwarded-For/Proto. Прокси должен перезаписывать эти заголовки сам.
Для удалённого PostgreSQL настрой SSL Mode=VerifyFull и доверенный корневой
сертификат. Шифрование полей не заменяет TLS соединения с базой.

## Проверки

В тестах проверяются реальные PostgreSQL-миграции, Identity/CSRF/права,
транзакции и квоты, SignalR двумя клиентами, контроль редактора, курсоры,
журнал/replay, TTL, шифрование строк и обнаружение подмены ciphertext.
Docker-тесты выполняют только синтетические программы на семи языках,
проверяют лимиты, сеть, read-only корень и отсутствие переноса файлов.
Это функциональная проверка ограничений, а не формальный аудит безопасности.
Проверка базы уязвимостей NuGet в данной среде сообщала о недоступном индексе;
перед публикацией повтори restore/audit с доступом к NuGet.
